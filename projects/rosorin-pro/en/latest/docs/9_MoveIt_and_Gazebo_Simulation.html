9.3 URDF Model Basics ​

9.3.1 Introduction to the URDF Model ​

NOTE

This tutorial is based on virtual machine configuration and simulation. If the virtual machine has not been installed yet, first install it by referring to Section 9.1 Virtual Machine Installation and Import.

  • URDF Model Overview

URDF stands for Unified Robot Description Format, an XML-based specification used to describe robot structures. Its objective is to provide a standardized, universally applicable description of robot hardware.

Robots are typically modeled as kinematic structures composed of multiple links and joints. A link represents a rigid body with mass, while a joint connects two links and constrains their relative motion.

Connecting and constraining multiple links through joints forms a kinematic robot model. A URDF document describes the relative spatial relationships, inertial properties, geometric dimensions, and collision models across all joints and links.

  • Comparison Between Xacro and URDF Models

The URDF format provides a straightforward robot model description characterized by a clear and accessible structure. When describing complex robot structures, however, a pure URDF document becomes lengthy and redundant.

The Xacro model is an XML macro extension of the URDF format, sharing an identical underlying representation. Describing a robot using Xacro streamlines model definitions through parameterized macros, enhancing code reusability and eliminating URDF redundancy.

For example, when modeling both legs of a humanoid robot, standard URDF requires defining each leg individually from scratch. With Xacro, a single parameterized leg macro is defined and instantiated twice.

  • Basic URDF Syntax
  1. XML Basic Syntax

Because the URDF model is written based on the XML specification, understanding the basic structure of XML is essential.

  1. Elements can be defined with designated names according to the following syntax rules:

<element>

</element>

  1. Attributes are encapsulated inside elements to define properties and parameters, using the following syntax structure:

<element attribute_1="value1" attribute_2="value2">

</element>

  1. Comments do not affect other attributes or elements, and follow this syntax rule:

<!-- Comment content -->

  1. Link

A link is defined using the <link> tag in a URDF model. It describes the visual appearance and physical properties of a rigid robot component. Defining link behaviors involves the tags shown below:

<visual>: Describes visual parameters of the link, including size, color, and geometric shape.

<inertial>: Describes inertial parameters of the link, primarily used for robot dynamics computations.

<collision>: Describes collision properties of the link.

Each tag contains corresponding sub-tags and functions, as outlined in the following table:

TagFunction
originDescribes link pose, containing two parameters where xyz defines the position in the simulation map and rpy defines the orientation.
massDescribes the mass of the link.
inertiaDescribes link inertia. Due to rotational symmetry of the inertia matrix, six attributes ixx, ixy, ixz, iyy, iyz, and izz must be specified through calculation.
geometryDescribes link geometry, using the mesh parameter to load mesh files and filename to specify the file path. It also contains three basic shape sub-tags: box, cylinder, and sphere.
materialDescribes link visual material, where the name attribute is mandatory. Color and transparency are adjusted via the color sub-tag.
  1. Joint

A joint is defined using the <joint> tag in a URDF model. It describes kinematic and dynamic properties of the robot joint, as well as position and velocity limits. Based on the type of motion, joints are classified into the six categories listed in the table below:

Type and DescriptionTag
Continuous joint: allows continuous rotation around a single axis without limits.continuous
Revolute joint: rotates around an axis with upper and lower angular limits.revolute
Prismatic joint: slides along a linear axis with position limits.prismatic
Planar joint: allows translation or rotation perpendicular to a designated plane.planar
Floating joint: allows unrestricted 6-DOF translation and rotation.floating
Fixed joint: locks all degrees of freedom and forbids relative motion.fixed

Defining joint behaviors involves the tags shown below:

<parent_link>: The parent link.

<child_link>: The child link.

<calibration>: Used to calibrate joint angles.

<dynamics>: Describes physical properties of motion.

<limit>: Describes operational limits of motion.

Each tag contains corresponding sub-tags and distinct functions, as outlined in the following table:

TagFunction
originDescribes joint pose relative to the parent link, containing parameters xyz for position and rpy for orientation in the simulation map.
axisSpecifies the rotation axis of the child link relative to the parent link along the x, y, or z axis.
limitSets motion limits for the child link. The lower and upper attributes specify the angular range in radians. The effort attribute sets the maximum force in N. The velocity attribute specifies the maximum velocity in m/s or rad/s.
mimicSpecifies coupling relationships between this joint and another joint.
safety_controllerSets safety parameters to protect joint movement during robot operation.

9.4 MoveIt2 Simulation ​

9.4.1 MoveIt2 Kinematics Design ​

  • Kinematics Introduction

Kinematics is a branch of mechanics that studies motion from a purely geometric perspective, without regard to the physical forces or masses involved, analyzing position variations over time. Forward kinematics and inverse kinematics represent two fundamental analytical methods in robotics.

Forward kinematics calculates the position and orientation of the end-effector given specific values for all joint variables, determining the final robot pose from servo rotation angles.

Inverse kinematics calculates the required joint variables given a target position and orientation of the end-effector, calculating servo angles backward from the desired pose.

  • Inverse Kinematics Analysis

(1) Geometric Method

For a robotic arm, inverse kinematics calculates the rotation angle of each joint based on the target position and orientation of the gripper. Because spatial 3D motion involves complex kinematics, the rotation joint of the lower pan-tilt base is temporarily omitted, allowing kinematic analysis on a two-dimensional plane.

Analytical inverse kinematics often requires intensive matrix operations that demand heavy computation. To satisfy operational requirements efficiently, the geometric approach is used to analyze the robotic arm.

(2) DH Modeling Method

① Introduction

The Denavit-Hartenberg parameter table, referred to as the DH parameter convention, is a standardized method for describing the relative position and orientation between adjacent joints and links of a robotic arm. It defines the kinematic relationship between consecutive joints using four geometric parameters:

  1. Link length: The length of the common normal between the axes of two consecutive joints, whether revolute or prismatic.

  2. Link twist: The angle between the axes of two joints measured around their common normal.

  3. Link offset: The distance along the axis of a joint from the common normal of the preceding joint to the common normal of the next joint.

  4. Joint angle: The angle around the joint axis between the common normal of the preceding joint and the common normal of the next joint.

Two critical lines form the foundation of this convention: the joint axis and the common normal between the axes of adjacent joints.

Under the DH parameter convention, the joint axis is designated as the z-axis, and the common normal is designated as the x-axis, oriented from the current joint toward the subsequent joint.

These two rules alone do not fully determine the coordinate frame of each joint. The detailed procedure for establishing joint coordinate frames is described below.

Alternative coordinate conventions exist in robotic simulation, but mastering this method provides essential kinematic foundations for subsequent analysis.

The figure below illustrates two representative robot joints. Although such links and joints may not correspond directly to specific physical robots, they represent any standard robotic joint mechanism.

② Coordinate Frame Determination

Establishing coordinate frames involves the following sequential steps:

To model a robot using DH representation, first assign a reference coordinate frame to each joint by specifying a z-axis and an x-axis.

Assign the z-axis: If the joint is revolute, the z-axis aligns with the axis of rotation according to the right-hand rule, and the rotation angle around the z-axis serves as the joint variable. If the joint is prismatic, the z-axis aligns with the direction of linear motion, and the link displacement d along the z-axis serves as the joint variable.

Assign the x-axis: When two joint axes are neither parallel nor intersecting, their z-axes are skew lines, yet a unique shortest common normal line always exists perpendicular to both skew axes. Define the x-axis of the local reference frame along this common normal. If an denotes the common normal between Zn−1 and Zn, the direction of Xn aligns with an.

Special geometric conditions also apply. When the z-axes of two consecutive joints are parallel, infinite common normals exist. Selecting the common normal collinear with that of the preceding joint simplifies the kinematic model. When two joint axes intersect, no common normal exists between them. Defining the line perpendicular to the plane formed by the two intersecting axes as the x-axis simplifies the kinematic model.

After assigning corresponding coordinate frames to each joint, the system is configured as shown below:

With coordinate frames established, the four parameters are concisely defined:

Link length li: The distance along the positive Xi−1 axis from the Zi−1 axis to the Zi axis.

Link twist ai: The twist angle around the positive Xi−1 axis from the Zi−1 axis to the Zi axis according to the right-hand rule.

Joint distance di: The distance along the positive Zi−1 axis from the Xi−1 axis to the Xi axis.

Joint angle θi: The rotation angle around the positive Zi−1 axis from the Xi−1 axis to the Xi axis according to the right-hand rule.

9.4.2 MoveIt2 Configuration ​

  • MoveIt2 Overview

MoveIt 2 is an open-source robotic motion planning framework designed specifically for ROS 2, providing advanced motion control and path planning capabilities. It represents the ROS 2 evolution of MoveIt, a widely adopted motion planning framework in ROS.

Compared to MoveIt 1, MoveIt 2 delivers enhanced real-time control capabilities supported by core ROS 2 architectural improvements, ensuring precise and reliable robot motion execution. ROS 2 adopts DDS as its communication middleware, which MoveIt 2 leverages to enable flexible and efficient data transmission.

MoveIt 2 provides an accessible platform for developing sophisticated robotics applications, evaluating robot structural designs, and building integrated robotic products. It is broadly deployed across industrial, commercial, and research sectors, serving as a prevalent manipulation framework.

MoveIt 2 offers mature plugins and configuration utilities that streamline robotic arm integration, along with rich APIs facilitating secondary development on the MoveIt 2 framework.

(4) Robot Poses

(5) Passive Joints

Defines unactuated passive joints, distinguishing active control joints from passive structures.

(6) ROS 2 Controllers

(7) ros2_control URDF Modifications

Configures URDF modifications required for hardware interface simulation.

9.4.5 MoveIt2 Cartesian Path Planning ​

  • MoveIt2 Cartesian Path Overview

Cartesian path planning is a trajectory generation method based on moving the robot end-effector through Cartesian space.

In MoveIt 2, Cartesian path planning specifies start and goal poses of the robot end-effector, generating a smooth continuous trajectory from the starting pose to the target pose.

(1) Cartesian Coordinate System

The Cartesian coordinate system encompasses rectangular and oblique coordinate frames. Two intersecting numerical axes sharing an origin form an affine planar coordinate frame. When measurement units along both axes are equal, the system is designated as a Cartesian coordinate frame. When the axes are mutually perpendicular, it is a Cartesian rectangular coordinate frame.

Describing spatial positions, velocities, and accelerations typically relies on the Cartesian coordinate system. Angular rotation around a coordinate axis follows the right-hand rule, as shown below:

(2) Cartesian Path Analysis

Cartesian path planning is divided into point-to-point planning and continuous path planning based on trajectory characteristics. By defining target points or trajectories, kinematic computations generate joint-level trajectories to track desired paths.

When controlling each axis in joint space, axis motions are interpolated independently without coordinating intermediate shapes, resulting in arbitrary curved end-effector trajectories between points.

In specific manipulation tasks requiring straight-line or circular end-effector paths, Cartesian path planning must be applied with Cartesian path constraints.

  • This section applies Cartesian path constraints to trajectory planning, restricting the simulation model and physical robotic arm to linear end-effector motion.

(3) Cartesian Path Planning Procedure

  1. Set the motion group: Specify the target motion group in MoveIt 2. A motion group defines the controlled joint subset and kinematic degrees of freedom, restricting planning dimensions for stable control.

  2. Set path constraints: Path constraints can be applied if specific motion restrictions are required, such as maintaining fixed joint orientations.

  3. Specify start and goal poses: Define the target motion goal by setting starting and target poses for the robot end-effector in the robot coordinate system.

  4. Perform path planning: Calling MoveIt 2 planning interfaces generates Cartesian paths based on the robot kinematic model, constraints, and target poses.

  5. Execute trajectory: Send the planned trajectory to the robot controller to execute motion. The robot moves sequentially along the planned trajectory toward the target pose.

9.4.6 MoveIt2 Collision Detection ​

  • MoveIt2 Collision Detection Overview

Collision detection is a vital MoveIt 2 capability that leverages planned trajectories and environmental obstacle data to detect potential collisions, ensuring that the robot operates without colliding with surrounding objects or itself.

(1) Collision Detection Configuration

Collision detection in MoveIt 2 is configured within planning scenes using CollisionWorld objects. Collision computation is predominantly executed using the Flexible Collision Library, known as FCL, which serves as the primary collision checking backend in MoveIt 2.

(2) Collision Object Types

MoveIt 2 supports collision detection across multiple object representations:

  1. Meshes

  2. Basic geometric primitives, such as boxes, cylinders, cones, spheres, and planes

  3. Octomap representations, which can be incorporated directly for spatial occupancy checking

(3) Allowed Collision Matrix

The Allowed Collision Matrix, abbreviated as ACM, encodes binary flags specifying whether collision checks between object pairs are evaluated.

When an entry in the ACM is set to 1, collision detection between those two objects is disabled, whereas an entry of 0 enforces collision checking.

This section adds a collision primitive to evaluate collision avoidance behaviors on both the simulation model and the physical robotic arm.

(4) Collision Detection Procedure

  1. Robot description: Provide geometric and kinematic models using URDF files to specify robot joints, links, collision geometries, and sensor attachments.

  2. Environment modeling: Model the surrounding workspace, specifying obstacle geometries and positions for static or dynamic objects.

  3. Motion planning: Generate motion trajectories between specified start and goal states using MoveIt 2 motion planners.

  4. Collision checking: Evaluate each waypoint along candidate trajectories against robot and obstacle geometries.

  5. Collision avoidance: If a collision is detected, the planner adapts arm poses or re-plans the trajectory until a collision-free path is found.

9.4.8 MoveIt2 Trajectory Planning ​

  • Trajectory Planners Overview

(1) Open Motion Planning Library, OMPL

OMPL is a sampling-based open-source motion planning library implemented in C++. Its algorithms derive predominantly from Rapidly-exploring Random Trees and Probabilistic Roadmaps, including RRT*, RRT-Connect, and related planners.

Due to its modular architecture, frontend GUI integration, and active maintenance, OMPL serves as the standard motion planning framework in ROS.

Sampling-based planning avoids dimensionality explosion when evaluating high-degree-of-freedom systems, resolving trajectory problems under complex constraints efficiently. This makes OMPL particularly suitable for MoveIt 2 robotic arm manipulation.

For an N-degree-of-freedom robotic arm, OMPL computes a collision-free joint-space trajectory toward the target pose, where the trajectory comprises M waypoints, representing joint state sequences at each waypoint that guarantee collision-free execution.

(2) Pilz Industrial Motion Planner

The Pilz industrial motion planner is a deterministic trajectory generator for circular and linear Cartesian motions. It supports blending multiple motion segments within MoveIt 2 workflows.

(3) Stochastic Trajectory Optimization for Motion Planning, STOMP

STOMP is an optimization-based planner built upon the PI2 algorithm. It computes smooth trajectories, circumvents obstacles, and optimizes arbitrary cost terms without requiring derivative gradients.

(4) Search-Based Planning Library, SBPL

SBPL comprises generic motion planners that utilize search-based discrete graph search techniques to discretize state space.

(5) Covariant Hamiltonian Optimization for Motion Planning, CHOMP

CHOMP is a gradient-based trajectory optimization algorithm that resolves motion planning challenges through trajectory optimization.

Unlike traditional planners that decouple planning and trajectory smoothing, CHOMP optimizes trajectories directly using covariant gradients and functional gradient methods.

Given an initial candidate trajectory, CHOMP reacts to environmental collisions to steer the trajectory into free space while optimizing velocity and acceleration dynamics, rapidly converging toward smooth, executable paths.
